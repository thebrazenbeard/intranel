# Intranel V1 Implementation Plan

> **Historical implementation plan.** The original tasks below established the first `INTRANEL/1` candidate. Subsequent independent hostile review found material defects, so completion of this historical checklist must not be interpreted as current qualification. Current repaired executable source is `9cd1ba4d4da67c42bc9a186818c9229213b6c762`; see `2026-09-17-intranel-v1-hostile-repair.md` and the PR review record.

**Goal:** Build a dependency-light `INTRANEL/1` semantic protocol library with strict parsing, canonical content identity, deterministic receiver admission, schemas, hostile test vectors, and a Bus transport profile.

**Architecture:** Implement the protocol as a small Python 3.12 package. Keep semantic validity separate from receiver-side authority/security checks. Canonical JSON provides the first exact representation; binary codecs and cryptographic implementations remain explicitly out of scope for V1.

**Tech Stack:** Python 3.12, standard-library core, `unittest`, `jsonschema` for test-only Draft 2020-12 parity verification, JSON Schema documents, Markdown protocol specs.

**Spec:** `docs/superpowers/specs/2026-09-17-intranel-v1-design.md`

## Global Constraints

- Protocol identifier is exactly `INTRANEL/1`.
- Unknown fields and unsupported protocol versions fail closed.
- Intranel messages never create authority by transport or syntax alone.
- `origin`, `actor`, `target`, and `reply_to` remain distinct semantics.
- `message_id` and `operation_id` remain distinct identities.
- Mutating requests require operation/idempotency and authority references according to the current normative protocol.
- No binary codec, encryption implementation, key management, deployment, or production cutover in V1.
- No hidden-chain-of-thought transport.
- No merge to `main` without Patrick's explicit merge authority.
